# Provisional MWF 0.6.4 planning

This file records deferred discussion so Issue 21 can finish without presenting
future behavior as current functionality. The exact MWF 0.6.3 versus 0.6.4
boundary and the corresponding Wayfinder shape remain unsettled. Revisit every
item in a dedicated grilling session after 0.6.1 is closed.

## Project setup and source placement

Explore a setup flow in which `mwf init` can create the initial graph and place
project and node README files in their agreed locations. The user should not
have to run `mwf graph src/graph.py` for the ordinary initial layout.

Explore an explicit source-location command, provisionally shaped like:

```text
mwf source src/graph/graph1.py --graph
mwf source src/sample_behavior --behavior
```

The final command names, migration rules, graph synchronization behavior, and
README generation rules need design review. This is not implemented in 0.6.1.

## Autostart and waiting work

Revisit autostarting as a node property rather than a property assigned while a
job is routed. Design waiting jobs and non-waiting jobs inside a Hoeflein
component so work can wait for other jobs or component conditions without
turning the public model into job-level autostart configuration.

The relationship between node membership, waiting classification, component
construction, readiness, recovery, and existing `waiting` and `wait_for`
behavior must be decided together. Current 0.6.1 behavior remains documented in
the README and graph architecture guide.

## Read-only and preview behavior

Review commands that describe themselves as read-only and fix narrow,
clearly isolated side effects where the correction has a small blast radius.
Defer deeper state and CLI architecture changes.

Build an explicit preview and no-write matrix for graph, execution planning,
cleanup, recovery, migration, engine, inspection, and monitoring commands. The
matrix should distinguish imports, layout creation, database creation, journal
reads, network listeners, browser launch, and durable writes.

## Public API and engine coverage

Settle a public Python API compatibility policy, including aliases, removals,
versioning expectations, and the relationship between documented and exported
names. Do not infer long-term compatibility from the current lazy exports.

Decide the browser-level acceptance matrix for `mwf engine`, including graph
rendering, component reveal, loopback restrictions, absent mutation endpoints,
offline assets, and no project-code import.

## Command and queue architecture

Review the queue and command changes emerging from Issue 44 before fixing the
version boundary. Restart recovery, cleanup, waiting behavior, and later command
composition may depend on that work. Do not pre-empt Issue 44 here.

## Example and Kaicenat adoption

Example implementation remains planned for 0.6.3. It must remove the mistaken
`project provenance` concept from the reference-architecture example and replace
that output-history framing with the output-provenance principles settled in
0.6.1. The later planning session must decide whether any example work moves
across the boundary.

Kaicenat adoption is intentionally not decided in Issue 21. The later session
must consider its project and node READMEs, an AFSR system, MWF version update,
Issue 44 interactions, and replacement of `latest_hook_model_failure.json` with
live or durable MWF failure history when sufficient. If a temporary failure
record is still required, it should live under the node output prefix and be
removed after recovery succeeds.

## Decisions the later grilling session must produce

- the exact feature lists for 0.6.3 and 0.6.4;
- the updated Wayfinder routes for both releases;
- which Issue 18 items move to each release;
- the relationship with Issue 44;
- the Kaicenat adoption sequence and verification boundary;
- whether additional GitHub issues are needed or the plan file is sufficient.
