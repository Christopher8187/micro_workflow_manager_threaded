# Agent testing and diagnosis guide

This file is the required testing protocol for automated contributors working on
micro-workflow-manager. Read it before changing scheduler, storage, runner,
clipboard, deployment, monitoring, timeout, retry, fallback, or CLI behavior.

The goal is not merely to make one test invocation green. The goal is to collect
enough experimental evidence to distinguish a framework defect from test-harness
pressure, an unrealistic timeout, external blocking, or a mistake in the test
itself, then make the smallest durable fix and preserve MWF's guarantees.

## Core guarantees that tests must protect

- `input/`, `output/`, job `input.json`, job `output.json`, and returned files stay
  ordinary inspectable files.
- Scheduler-owned high-churn state stays transactional in `.mwf/state.sqlite3`.
- Graph and top-level node-folder changes remain explicit through `mwf graph`.
- One CLI sequence owns the project run slot; `mwf restart` is a second-terminal
  control for running or failed jobs inside that live sequence and never starts
  a competing scheduler.
- Restart, timeout, and recovery generation-fence abandoned attempts from later
  MWF-managed commits.
- Retry and fallback handlers preserve chronological events and terminal errors.
- Hoeflein components are computed as SCCs after explicit autostart edges add
  reverse reachability; the quotient keeps original dependency directions.
- Naming one member runs the whole component; member nodes run, complete, and
  fail as one lifecycle unit.
- Fresh cleanup fully resets every remaining job in the explicitly selected start
  component, while descendant merge cleanup removes selected-producer work and
  preserves jobs generated by unselected branches.
- `max_threads` remains the source-facing concurrency term for threaded, API, and
  process runners, even where it semantically means in-flight API calls.
- Cleanup, clipboard, migration, deployment, inspection, monitoring, and repeat
  command use must remain compatible with SQLite-backed state.

## Required workflow for every code change

1. Identify the behavior and invariants affected by the change.
2. Read the closest existing tests before editing code.
3. Decide whether an existing test should be upgraded or merged, or whether a
   focused new regression test is clearer. Do not add redundant tests merely to
   increase test count.
4. Make the smallest implementation change that satisfies the behavior.
5. Run the focused tests first.
6. Exercise the command repeatedly and in more than one context where relevant.
7. Run the ordinary regression suite.
8. Run timing-sensitive cyclic tests separately rather than hiding their signal
   inside one overloaded harness process.
9. Update README.md, DESIGN.md, command help, and this guide when semantics or the
   recommended testing workflow changed.

A code change is incomplete until its test impact has been explicitly considered.
Routine refactors, code-architecture improvements, and test consolidation do not
require a special human escalation document.

## Standard test commands

Run the ordinary suite without combining the timing-sensitive cycle file:

```bash
python -m pytest -q --ignore=tests/test_autostart_cycles.py
```

Run every cyclic/autostart test in a fresh process. A fresh process avoids one
large test's thread, timing, or executor pressure contaminating the next result:

```bash
python -m pytest -q tests/test_autostart_cycles.py::test_runfrom_supports_self_and_mutual_autostart_cycles_before_downstream
python -m pytest -q tests/test_autostart_cycles.py::test_threaded_diamond_cycle_spawns_100_seed_jobs_without_deadlock
python -m pytest -q tests/test_autostart_cycles.py::test_threaded_ring_cycle_spawns_100_seed_jobs_without_deadlock
python -m pytest -q tests/test_autostart_cycles.py::test_threaded_stochastic_game_engine_spawn_cycle_finishes
```


Run the Hoeflein foundation tests whenever scheduling, cleanup, provenance, or
autostart behavior changes:

```bash
python -m pytest -q tests/test_036_hoeflein_scheduling.py
```

These tests must cover at least:

- `A -> C` plus `B autostarts C`, yielding quotient `A -> {B,C}`;
- refusal to start `{B,C}` before A completes;
- automatic component-autostart for an ordinary internal edge;
- `A -> C` and `B -> C` branch reruns preserving the other producer's jobs;
- repeated `runfrom` cleanup without accumulation or collateral deletion;
- whole-component failure after one member job fails.

Run the marked long stress test explicitly rather than accidentally including it
in every edit cycle:

```bash
python -m pytest -q -m stress tests/test_markov_chain_stress.py
```

Deployment, clipboard, thread-refresh, and monitor changes should also run their
focused files at least twice when they manipulate persistent state:

```bash
python -m pytest -q tests/test_deploy.py tests/test_init_clipboard_debug_028.py tests/test_runtime_thread_overrides.py tests/test_cli_monitor.py
python -m pytest -q tests/test_deploy.py tests/test_init_clipboard_debug_028.py tests/test_runtime_thread_overrides.py tests/test_cli_monitor.py
```

## Use inline monitoring as experimental evidence

For a full timestamped timeline in the same terminal:

```bash
mwf run NODE --monitor
mwf runfrom NODE --monitor
mwf run NODE --monitor --monitor-interval 0.5
```

Inline monitoring never clears prior output. Each snapshot shows the exact
observation time, active run, running nodes and job IDs, queue/running/done/failed
counts, progress, effective concurrency, average duration, and rough ETA. The
terminal snapshot must say `active run: none` after the run record becomes
terminal.

Use compact statistics when a full table would be too noisy:

```bash
mwf runfrom NODE --stats --stats-interval 1
```

Use a second-terminal or post-failure snapshot when independent observation is
important:

```bash
mwf monitor --once
mwf monitor --json --once
mwf inspect NODE
mwf inspect NODE filter
mwf inspect NODE failed
mwf inspect NODE job ID
```

Preserve monitor output from before, during, and after the suspected stall. A
single final status is not enough to diagnose a scheduling freeze.

## Failure-triage ladder

A harness timeout or one slow CI run is evidence, not a diagnosis. Before changing
framework semantics, perform controlled experiments in this order where they are
applicable.

### 1. Reproduce narrowly

Run the exact failing test by itself. Repeat it. Note whether the failure is
reproducible, intermittent, or only appears after other tests. Then run the same
behavior through a small runnable project with `--monitor` so the scheduler state
at each time is visible.

### 2. Test compute and concurrency pressure

Reduce concurrency first and compare behavior:

```bash
mwf threads NODE 1
mwf runfrom NODE --monitor
mwf threads NODE reset
mwf threads --api-total 128
mwf threads --api-total reset
```

For source-level experiments, temporarily lower `max_threads` in the node router
and refresh declarations with:

```bash
mwf threads --update
```

Compare at least `1`, a moderate value, and the original value when feasible. If
lower concurrency reliably fixes the test, investigate resource saturation,
executor growth, SQLite contention, operating-system thread limits, or the test's
own workload before declaring a scheduler deadlock. Do not permanently reduce
concurrency without explaining the observed ratio and throughput tradeoff.

For API components, distinguish the node limit from the shared admission budget.
Several nodes can each be configured at 100 while the workflow admits only 256
provider calls in total. Tune `--api-total` first when all API nodes slow down
together; tune one node when only that queue needs a different share.

For progressive degradation, repeat the same synthetic round in one Python
process and record elapsed time, live thread count, and the number of registered
SQLite connections after each round. Framework-created worker, handler,
supervisor, component, and inline-monitor threads must release their connection
when they exit. A checkpoint should perform one runtime-row write, and a
restart-fenced payload write must not create SQLite advisory-lock rows.

### 3. Test timeout policy separately

Determine which timeout fired: test-harness timeout, task total timeout, dynamic
checkpoint deadline, external HTTP/client timeout, or a join used only by the
test. Temporarily increase or disable only the suspected experimental timeout,
then compare monitor and event history.

A passing test after increasing an outer harness timeout does not prove the
framework is correct; it may merely conceal a freeze. A passing test after
changing a checkpoint deadline does not prove the checkpoint was wrong; inspect
whether progress was actually being reported. Use `mwf inspect NODE job ID` and
the event timeline to identify the responsible boundary.

### 4. Compare runners and workload shape

Where semantics permit, compare direct, threaded, API, and process modes. Reduce
seed count or cycle duration to determine whether the problem scales smoothly or
appears at a specific threshold. Preserve the original high-load regression once
the cause is known; a smaller diagnostic case may be added alongside it.

### 5. Distinguish test-code freezing from framework freezing

Look for accidental barriers, locks held across waits, unbounded job creation,
probability rules that never terminate, blocking reads without client timeouts,
mock callbacks that wait for the scheduler thread, and assertions that consume or
block output pipes. Verify that the monitor thread remains responsive and that
`.mwf/run.json` heartbeat time advances.

For component scheduling failures, record the augmented autostart graph, the
Hoeflein component membership, quotient edges, producer component on each job,
and whether the command is a strict start-component run or a partial descendant
runfrom. A test that reasons only from raw node edges is incomplete.

Framework-level warning signs include a live heartbeat with no state transition,
queued work in a ready component with no worker launch, all worker/controller
threads waiting on a framework-owned lock, a generation that can no longer be
claimed, or a component that is quiescent but never finalized. Test-level warning
signs include jobs continuing to transition normally while the harness is blocked,
only captured-output mode hanging, or the test's own probability/timeout logic
preventing termination.

### 6. Fix from evidence

Use the experiments to choose the fix. Add or upgrade a regression test that
fails for the identified reason, not merely for the original wall-clock symptom.
Avoid replacing deterministic state assertions with longer sleeps.

## Repeat-use matrix

Stateful commands must be tested beyond a single clean invocation. Depending on
the change, include several of these checks:

- Run the same node two or three times.
- Run two different nodes independently.
- Run `runfrom` twice and verify producer-component jobs are selectively rebuilt, while jobs from unselected producers remain unchanged.
- Mix `run`, `runfrom`, `resume`, and `resumefrom` after done, failed, and queued
  states; verify fresh commands rerun external-parent jobs in the start component
  and resume commands requeue failed jobs without a prior restart.
- Run selected jobs, ranges, and then the whole node.
- Apply `mwf threads --update` repeatedly, with and without a runtime override.
- Use `mwf copy`/`mwf paste` repeatedly and immediately inspect and run the node.
- Build `mwf deploy local` twice and validate archive replacement and filtering.
- Run monitor before a run, during it, after completion, and after a second run.
- Reopen storage through a new CLI invocation to catch stale in-memory caches.

Tests should verify both the command result and durable state in SQLite/files. Also
check for leaked reporter, worker, heartbeat, or abandoned orchestration threads
when the change touches lifecycle management.

## Timing-sensitive test design

- Prefer events, barriers, and state polling over arbitrary sleeps.
- Put an outer timeout around tests that can deadlock, but retain monitor/events
  needed to explain the timeout.
- Use deterministic random seeds or deterministic probability functions.
- Keep quick regression cases small; keep a separate explicit stress test for
  sustained load.
- Run large cycle tests in separate processes.
- When a test is intentionally slow, document the reason and the expected state
  transitions, not only the allowed duration.

## Rare stubborn-issue escalation

Create `STUBBORN_ISSUE.md` only when experimental evidence shows that satisfying a
request would require changing a fundamental MWF philosophy or making mutually
incompatible guarantees. This is rare. Routine refactors, storage redesigns,
runner changes, and ordinary architecture work do not qualify.

The file must state:

1. the exact prompt criteria that are not met;
2. the smallest reproducible project and commands;
3. monitor, inspect, thread-count, runner, and timeout experiments performed;
4. which fundamental guarantees conflict and why;
5. parts that work and parts that fail;
6. at least two plausible code-philosophy changes, with compatibility and
   migration consequences;
7. a recommended human decision.

Do not use this file as a substitute for trying reasonable fixes. Return it only
with all safe partial improvements and regression tests already completed.

## Live API refill regression

When testing a high-fanout Hoeflein component, do not only assert that a handler
starts before its router finishes. Route jobs gradually, keep handler calls long
enough that the first pump remains alive, and assert that the handler's in-flight
count grows toward its configured API limit while routing is still in progress.
This catches static queued-job snapshots that superficially look like live
component pumping but leave hundreds of later jobs queued.


## Waiting nodes and cleanup invariants (0.3.16)

- Treat a Hoeflein component as the minimum unit for `clean`, `reset`, and
  `wipe`; tests must include a multi-node cycle selected by one member.
- Waiting dependencies must be peers in the same component. Do not reinterpret
  them as DAG predecessor edges.
- Keep waiting jobs in job status `queued`; only node/monitor lifecycle status
  is `waiting`.
- Check waiting gates at node-pump admission, not before every job, so an active
  pump cannot deadlock halfway through its queue.
- Test restored mutual-wait states where both sides already have queued work and
  verify deterministic bootstrap plus eventual quiescence.


## Queue and transport scaling checks (0.3.17)

- Test live component handoff with the polling fallback deliberately set high;
  the consumer must start from the queue-change notification while its producer
  is still running.
- Test progressive, not only simultaneous, future completions. The number of
  completion probes must remain linear in the number of futures.
- Keep job state and event history atomic inside grouped mutations. A failure in
  one savepoint must not roll back unrelated valid mutations in the same batch.
- Active restart polling must remain one lease snapshot per supervisor interval,
  never one SQLite query per active controller or fiber.
- Test HTTP sharding with an in-flight barrier. No client may exceed
  `streams_per_connection`, enough clients must be created to carry the wave,
  and node `max_threads` must remain the only concurrency ceiling.


## High-fanout component scaling checks (0.3.18)

- Fresh component preparation must read parent/provenance metadata in one
  SQLite snapshot and reset or delete selected jobs in batches. Never restore a
  per-job metadata query or one transaction per retained/deleted job.
- Fiber cancellation checks are fallback polling, not an admission-loop scan.
  Keep callback-driven future completion and heap-backed wakeup deadlines so a
  wave of thousands of API jobs remains linear.
- Queue pumps must preload metadata with a bounded batch query. Do not restore
  a `read_job_metadata` query between every queued ID and its execution claim.
- Keep single-child publication atomic: stage the payload first, then allocate
  its ID and publish payload/row/event/sequence in one priority mutation. Do not
  expose a job row before its input exists.
- Writer batches contain one priority class. Queue publication must not absorb
  lower-priority API claim/checkpoint work simply because a transaction has
  spare batch capacity.
- Batched claims and terminal updates retain per-job generation/execution
  checks. A stale entry must not roll back or suppress valid peers in its batch.
- Never hold a per-job filesystem execution fence while yielding for grouped
  SQLite persistence. Publish files under the fence, release its OS handle, and
  then perform the conditional terminal mutation using the same execution ID.
- `ctx.side_effects()` is for a short group of local publications that must be
  restart-atomic. Do not hold it across HTTP requests, sleeps, or substantial
  computation.
- Add monitor-shaped regressions as well as small unit cases: thousands of jobs
  distributed unevenly across one Hoeflein component must all reach execution,
  and a simultaneous completion wave must not exhaust file descriptors.


## Adaptive API admission checks (0.4.1)

- Keep the initial refreshable-source admission probe at 64, the sparse floor at
  16, and the dense ceiling at 1024 unless benchmarks justify changing all three.
- A full pull may grow the next window geometrically. A partial or empty pull
  must return the next probe to 16 so trickling producers are not polled through
  oversized claim transactions.
- Admission tuning must not reuse the terminal finalization coordinator or lower
  terminal mutation priority. Output-backed completions must become visible even
  while the next admission pull is blocked or dense claims continue.

## Monitor terminal-state checks (0.4.0)

- Keep API claim/checkpoint mutations below terminal status mutations in the
  grouped writer. A large node that is still starting jobs must not make its
  completed output appear permanently `running` to `mwf monitor`.
- Keep durable queue publication above both terminal and consumer state churn so
  monitor visibility does not regress live Hoeflein producer throughput.
- Test the priorities through the real supervised API execution path and assert
  the final monitor snapshot has exact done/queued/running counts.
